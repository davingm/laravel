## Getting Started

Before contributing, please:

1. Read the available [framework feature guides](docs/README.md) before changing related behavior. Documents under `docs/discussion/` may be outdated or still under review.
2. Search existing [issues](https://github.com/davingm/laravel/issues) and [pull requests](https://github.com/davingm/laravel/pulls) to avoid duplicating effort.
3. Open an issue before starting work on a significant change. This allows the maintainers to discuss the direction before implementation begins.

## How to Contribute

### Types of contributions welcome

- Bug fixes
- Documentation improvements
- Performance improvements
- New features that align with the project's conventions
- Test coverage improvements

### Types of contributions that require prior discussion

- Changes to the public API surface (CLI commands, Artisan commands, Blade directives)
- Changes to the PageRouter file-system routing conventions
- Changes to the Frontend payload structure
- New dependencies

## Development Setup

**Requirements:**

| Dependency | Version |
|---|---|
| PHP | >= 8.3 |
| Composer | >= 2.x |
| Node.js | >= 20.19 or >= 22.12 |

**Setup from a fresh checkout:**

```bash
git clone https://github.com/davingm/laravel.git
cd laravel
cd playground
composer run setup
```

`playground/` is the Laravel application used to develop and test the framework. Run Composer, npm, and Artisan commands from that directory. `composer run setup` installs dependencies, creates local environment and SQLite files when missing, generates an application key, runs migrations, and builds frontend assets. Run it once for a fresh checkout; before running it again, check your `.env` and database because setup runs migrations and may change local application configuration.

**Start development environment:**

```bash
cd playground
artisan dev
```

This custom CLI starts the Laravel server, queue worker, and Vite dev server in one terminal. Its launcher is generated by Composer's autoload hook. If `artisan` reports that no project was found, refresh the launcher from `playground/` and retry:

```bash
node .laravel/setup.js
artisan dev
```

In the monorepo, invoke the command from `playground/`; the launcher searches the current directory and its parents for `.laravel/cli.js`.

### Dev Container

The repository provides an isolated PHP, Composer, Node.js, and SQLite development environment:

1. Install Docker Desktop or another compatible container engine, Visual Studio Code, and the Dev Containers extension.
2. Open the repository root in VS Code.
3. Run **Dev Containers: Reopen in Container**. On first creation, the container runs `composer run setup` in `playground/`.
4. Open a container terminal and run:

   ```bash
   cd playground
   composer run dev
   ```

The application is served on port `8000`. To rebuild the container after changing its base image or features, use **Dev Containers: Rebuild Container**. See `.devcontainer/devcontainer.json`.

If you prefer not to use a container, install the requirements listed above and follow the host setup instructions.

## Coding Standards

### PHP

- Follow PSR-12 code style.
- All code is formatted with [Laravel Pint](https://laravel.com/docs/pint). Run it before committing:

```bash
vendor/bin/pint --dirty
```

- Use PHP 8.x constructor property promotion and match expressions where appropriate.
- All public methods must have explicit return type declarations and typed parameters.
- Use PHPDoc blocks for complex logic, not inline comments.

### Blade

- File-based pages belong in `src/pages/`, layouts in `src/layouts/`, and shared components in `src/components/`.
- Follow the existing layout and page conventions. The main layout provides `content`, `seo`, and `title` sections; add an `@section('seo')` when a page needs custom metadata.
- Use the Laravel view and include patterns already present in the area you are changing.

### JavaScript

- The Vite JavaScript entry point is `src/assets/js/app.js`. Keep it small and follow the existing vanilla JavaScript approach.
- Do not introduce npm dependencies without prior discussion.

### CSS

- The Vite CSS entry point is `src/assets/css/app.css`; `vite.config.js` defines both asset entry points.
- Tailwind CSS 4 is already part of the frontend stack. Follow the existing Tailwind utility conventions and use plain CSS for custom component rules.
- Do not add another CSS framework or build tool without prior discussion.

## Commit Messages

Use the [Conventional Commits](https://www.conventionalcommits.org/) specification:

```
<type>(<scope>): <short summary>
```

**Types:**

| Type | When to use |
|---|---|
| `feat` | A new feature |
| `fix` | A bug fix |
| `docs` | Documentation changes only |
| `refactor` | Code change that is neither a bug fix nor a new feature |
| `test` | Adding or updating tests |
| `chore` | Build process, tooling, or dependency changes |
| `perf` | Performance improvements |

**Examples:**

```
feat(make:page): add --force flag to overwrite existing pages
fix(page-router): normalise Windows backslashes in path resolution
docs(reference): document exclude pattern behaviour
test(page-router): add coverage for wildcard exclude patterns
```

## Pull Request Process

1. Fork the repository and create a branch from `main`.
2. Name your branch descriptively: `fix/page-router-windows-paths`, `feat/make-page-force-flag`.
3. Make your changes with appropriate test coverage.
4. From `playground/`, ensure all tests pass:

```bash
node .laravel/cli.js test
```

5. Run Pint to format your code:

```bash
vendor/bin/pint --dirty
```

6. Update documentation if you are changing behaviour or adding features.
7. Open a pull request against `main` with a clear title and description.
8. Reference any related issues using `Closes #123` in the PR description.
9. A maintainer will review your pull request. Be prepared for feedback and revisions.

Add or update tests for behavior changes. If a check cannot reasonably be run, explain why in the pull request rather than implying it passed. Run Pint for PHP changes and include the result in the pull request description when practical.

---

Do not create release tags as part of an ordinary contribution. The runtime package has its own release repository and process; consult [the runtime package release guide](docs/dev/publish-runtime-package.md) and verify current tags and registry metadata before preparing a release. The package split discussion is historical and is not release guidance.

## Reporting Bugs

Use the [bug report form](https://github.com/davingm/laravel/issues/new?template=bug_report.yml). Search existing issues first. Do not post credentials, personal data, production secrets, or security vulnerabilities in a public issue.

A good bug report includes:

- A clear and descriptive title
- The PHP, Composer, and Node.js versions you are using
- The exact steps to reproduce the issue
- The expected behaviour and what you observed instead
- Relevant output, error messages, or stack traces

For security vulnerabilities, do **not** open a public issue. See [SECURITY.md](SECURITY.md).

## Feature Requests

Use the [feature request form](https://github.com/davingm/laravel/issues/new?template=feature_request.yml). Describe:

- The problem you are trying to solve
- The proposed solution
- Alternatives you have considered

Features that significantly expand the scope or add dependencies should be discussed with maintainers before implementation.

## Code of Conduct

Participation in this project is subject to the [Code of Conduct](CODE_OF_CONDUCT.md). Contact the maintainer privately using the options on the [GitHub profile](https://github.com/davingm) to report a conduct concern; do not disclose sensitive details in a public issue.
